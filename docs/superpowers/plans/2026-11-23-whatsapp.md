# Envois WhatsApp (facture, rappels, reçu) — plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** envoyer automatiquement sur WhatsApp (API Cloud de Meta) la facture, les rappels J-3/J/J+3/J+7 et le reçu, avec un journal visible sur la fiche facture.

**Architecture:** la règle « quel message aujourd'hui ? », les textes des modèles, la lecture du webhook Meta et sa signature sont des fonctions pures dans `src/lib/domain/whatsapp.ts`. Un client HTTP `src/lib/whatsapp.ts` (fetch injectable, style de `src/lib/campay.ts`) envoie un modèle et classe la réponse (envoyé / refus / incertain). Un répartiteur `src/lib/whatsapp-dispatch.ts` travaille sur une interface de stockage `WhatsappStore` : implémentation Supabase mince, et implémentation en mémoire pour les tests. La réservation atomique et la mise à jour des statuts sont des fonctions SQL `security definer` appelées par le serveur avec la clé service.

**Tech Stack:** Next.js 16, TypeScript, Supabase, Vitest, `node:crypto`.

**Spec:** `docs/superpowers/specs/2026-11-23-whatsapp-design.md`

## Global Constraints

- API Graph de Meta : `POST https://graph.facebook.com/<version>/<WHATSAPP_PHONE_NUMBER_ID>/messages`, en-tête `Authorization: Bearer <WHATSAPP_TOKEN>`. Version par défaut `v23.0`, surchargeable par `WHATSAPP_API_VERSION`.
- Corps d'envoi : `{ messaging_product: "whatsapp", to: <numéro sans "+">, type: "template", template: { name, language: { code: "fr" }, components: [{ type: "body", parameters: [{ type: "text", text }, …] }] } }`. Réponse attendue : `{ messages: [{ id: "wamid…" }] }`.
- Aucune nouvelle dépendance npm. HMAC avec `node:crypto`, comparaison `timingSafeEqual`.
- Secrets serveur uniquement : `WHATSAPP_TOKEN`, `WHATSAPP_APP_SECRET`, `WHATSAPP_VERIFY_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`.
- Dates « jour » au fuseau Douala (`todayIso()`), affichées `JJ/MM/AAAA` (`formatDate`), montants `formatXaf`.
- Textes visibles en français. Chaque commit passe `npm test`, `npm run typecheck` et `npm run build`.
- Un échec d'envoi WhatsApp ne fait jamais échouer l'émission des factures, l'enregistrement d'un paiement ou un webhook Campay (try/catch + `console.error`).

## Review Focus

- Deux déclenchements simultanés (cron + reçu immédiat, ou double clic « Renvoyer ») : un seul message par (facture, type).
- Réponse Meta ambiguë (timeout, 5xx, JSON sans `messages[0].id`) : ligne `incertain`, jamais renvoyée automatiquement.
- Webhook Meta avec signature absente, fausse ou calculée sur un autre corps : 401, rien modifié ; statuts arrivant dans le désordre (`delivered` après `read`) : le statut ne recule pas.
- Facture annulée, client sans numéro ou « ne pas contacter », espace désactivé, WhatsApp non configuré : aucun appel à Meta.
- Mise en service avec des factures en retard de plus de 7 jours : rien ne part.

### Task 1: Règle d'envoi et paramètres des modèles (logique pure)

**Files:**
- Create: `src/lib/domain/whatsapp.ts`
- Test: `src/lib/domain/whatsapp.test.ts`

**Interfaces:**
- Produces:
  - `type MessageKind = "facture" | "rappel_j-3" | "rappel_j" | "rappel_j+3" | "rappel_j+7" | "recu" | "renvoi"`
  - `type MessageStatus = "en_cours" | "envoye" | "remis" | "lu" | "echec" | "incertain" | "non_remis"`
  - `type SentMessage = { kind: MessageKind; status: MessageStatus; attempts: number; day: string }` (`day` = jour Douala de la dernière tentative)
  - `type InvoiceForRule = { status: "a_payer" | "payee" | "annulee"; issued_on: string; due_on: string; paid_at: string | null }`
  - `MAX_ATTEMPTS = 3`, `CATCH_UP_DAYS = 2`
  - `isBlocking(m: SentMessage): boolean` — vrai sauf pour `echec` avec `attempts < MAX_ATTEMPTS`.
  - `nextMessage(inv: InvoiceForRule, sent: SentMessage[], today: string): MessageKind | null`
  - `type TemplateCall = { name: string; params: string[] }`
  - `type InvoiceForTemplate = { number: string; label: string; amount_xaf: number; paid_xaf: number; due_on: string; paid_at: string | null; public_token: string; customer_name: string }`
  - `templateFor(kind: MessageKind, inv: InvoiceForTemplate, appUrl: string): TemplateCall`

Règle `nextMessage` (dans cet ordre) :
1. `annulee` → `null`.
2. `payee` → `"recu"` si `paid_at` et `0 ≤ today − paid_at ≤ CATCH_UP_DAYS` et aucun `recu` bloquant ; sinon `null`. Le reçu n'est pas soumis à la limite d'un message par jour.
3. `a_payer` :
   - `today > due_on + 7` → `null` (vieilles dettes).
   - un message bloquant (tout type, `renvoi` compris) dont `day === today` → `null`.
   - `facture` non bloquant et `0 ≤ today − issued_on ≤ CATCH_UP_DAYS` → `"facture"`.
   - sinon, parmi les rappels `[j-3: due−3, j: due, j+3: due+3, j+7: due+7]` dont la date est `≥ issued_on` et `≤ today`, prendre le plus récent ; si `today − date ≤ CATCH_UP_DAYS` et qu'il n'a pas de ligne bloquante → ce type ; sinon `null` (pas de repli sur un plus ancien).

Modèles (noms Meta, paramètres dans l'ordre ; `lien = <appUrl>/f/<token>`, `pdf = <appUrl>/api/factures/<token>/pdf`, `reste = amount_xaf − paid_xaf`) :
- `facture` et `renvoi` → `facture_emise` : `[customer_name, number, label, formatXaf(amount_xaf), formatDate(due_on), lien]`
- `rappel_j-3` → `rappel_avant_echeance` : `[customer_name, number, label, formatXaf(reste), formatDate(due_on), lien]`
- `rappel_j` → `rappel_echeance` : `[customer_name, number, label, formatXaf(reste), lien]`
- `rappel_j+3`, `rappel_j+7` → `rappel_retard` : `[customer_name, number, label, formatDate(due_on), formatXaf(reste), lien]`
- `recu` → `recu_paiement` : `[customer_name, formatXaf(paid_xaf), number, label, formatDate(paid_at), pdf]`

### Task 4: Base de données, stockage et répartiteur

**Migration :**
- `organizations.whatsapp_enabled boolean not null default false` ; `customers.whatsapp_opt_out boolean not null default false`.
- Table `whatsapp_messages` : `id uuid pk`, `org_id`, `invoice_id` (fk composite `(invoice_id, org_id)` → `invoices` on delete cascade, comme `payments`), `kind text check (in les 7 types)`, `phone text not null`, `template text not null`, `wamid text unique`, `status text not null default 'en_cours' check (in les 7 statuts)`, `error text`, `attempts integer not null default 1`, `created_at`, `updated_at timestamptz not null default now()`.
- Index unique partiel `(invoice_id, kind) where kind <> 'renvoi'`. Index `(invoice_id)`.
- RLS : `select` pour `is_member(org_id)` ; aucune écriture pour `authenticated`.
- `whatsapp_reserve(p_invoice uuid, p_kind text, p_phone text, p_template text) returns uuid` (security definer, `service_role` seulement) : lit `org_id` de la facture ; pour `renvoi`, insère toujours ; sinon `insert … on conflict (invoice_id, kind) where kind <> 'renvoi' do update set status = 'en_cours', attempts = whatsapp_messages.attempts + 1, phone, template, error = null, updated_at = now() where whatsapp_messages.status = 'echec' and whatsapp_messages.attempts < 3 returning id` ; renvoie `null` si rien réservé.
- `whatsapp_apply_status(p_wamid text, p_status text, p_error text) returns void` : rang `en_cours 0, envoye 1, remis 2, lu 3, non_remis 2` ; met à jour seulement si le rang du nouveau statut est supérieur à celui de l'actuel, ou si le nouveau est `non_remis` et l'actuel `envoye`/`en_cours`. `updated_at = now()`.
- `whatsapp_expire_stale() returns integer` : `en_cours` avec `updated_at < now() - interval '1 hour'` → `incertain`, `error = 'Envoi interrompu'`.
- `revoke … from public, anon, authenticated; grant execute … to service_role;` pour les trois fonctions (modèle : `20261123100000_campay.sql`).

**Interfaces:**
- Consumes: Tasks 1 et 3.
- Produces (`src/lib/whatsapp-dispatch.ts`) :
  - `type Candidate = InvoiceForRule & InvoiceForTemplate & { id: string; phone: string | null; opt_out: boolean; org_enabled: boolean; sent: SentMessage[] }`
  - `interface WhatsappStore { expireStale(): Promise<void>; candidates(today: string): Promise<Candidate[]>; candidate(invoiceId: string): Promise<Candidate | null>; reserve(invoiceId: string, kind: MessageKind, phone: string, template: string): Promise<string | null>; finish(id: string, result: SendResult): Promise<void> }`
  - `type Sender = (to: string, call: TemplateCall) => Promise<SendResult>`
  - `type DispatchDeps = { store: WhatsappStore; send: Sender; today: string; appUrl: string; configured: boolean }`
  - `runDaily(deps): Promise<{ sent: number; failed: number; uncertain: number }>` — `expireStale`, puis pour chaque candidat éligible (`configured`, `org_enabled`, `phone`, `!opt_out`) : `nextMessage` → `reserve` → `send` → `finish`. Une exception sur un candidat est journalisée et n'arrête pas les autres.
  - `sendReceiptIfDue(deps, invoiceId: string): Promise<void>` — même chemin pour une seule facture, seulement si `nextMessage` renvoie `"recu"`. Ne lève jamais.
  - `resendInvoice(deps, invoiceId: string): Promise<SendResult>` — lève une `Error` en français si non configuré, désactivé, sans numéro, opt-out, ou facture non `a_payer`. Type `facture` si aucun `facture` bloquant, sinon `renvoi`. `reserve` nul (double clic) → `Error("Envoi déjà en cours.")`.
- `src/lib/whatsapp-store.ts` : `supabaseStore(db: SupabaseClient): WhatsappStore`. `candidates(today)` : factures `a_payer` avec `due_on >= today − 7` et factures `payee` avec `paid_at >= today − 2`, jointes à `customers(name, phone, whatsapp_opt_out)`, `organizations(whatsapp_enabled)` et `whatsapp_messages(kind, status, attempts, updated_at)` ; `day` = `todayIso(new Date(updated_at))`. `finish` : `envoye` → `status, wamid` ; sinon `status, error`.
